발견한 문제와 후속 조치

높음신규 사용자는 첫 로그인에서 500 이 나서 가입할 수 없다 (E2E-004, 005)

auth.controller.ts 의 findOrCreateUser 가 신규 이메일일 때 실행하는 INSERT 에서 $1 을 두 곳에 쓴다. 하나는 auth.users.id(uuid 컬럼)에 들어가는 값이고, 다른 하나는 left($1::text, 6) 의 text 캐스트다. PostgreSQL 이 같은 파라미터를 uuid 와 text 로 동시에 추론하려다 inconsistent types deduced for parameter $1 (42P08)로 실패한다. username 충돌 여부와 무관하게 신규 가입은 모두 막힌다.

영향: 지금 DB 에 있는 7명만 로그인할 수 있고 새 팀원은 로그인할 수 없다. 배포용 deploy/docker-compose.yml 도 같은 postgres:18-alpine 이라 운영에서도 같을 가능성이 높다(운영 서버는 직접 확인하지 않았다).

수정안. 캐스트를 left($1::uuid::text, 6) 로 바꿔 파라미터 타입을 uuid 로 통일한다. 이 형태가 파싱되는 것은 PREPARE 로 확인했고(행 삽입 없음), 접미사 분기는 트랜잭션 ROLLBACK 으로 확인했다. 저장소 코드는 수정하지 않았다.

후속: 수정 후 E2E-004, 005 를 다시 수행한다. 모킹 방식은 아래 '실행 환경'의 서버 쪽 모킹을 그대로 쓰면 된다.

중간자동 테스트가 신규 가입과 대부분의 거부 경로를 보지 않는다

test/auth.e2e-spec.ts 는 기존 계정 로그인과 aud 불일치만 다룬다. 신규 사용자 생성, username 충돌 접미사, iss 불일치, email_verified=false, 토큰 교환 4xx, 쿠키 Secure 속성은 테스트가 없다. 이번 500 이 그동안 잡히지 않은 이유다. 신규 가입과 username 충돌 케이스부터 추가하는 것을 권한다. 테스트가 로컬 DB 에 쓰므로 정리 단계도 같이 넣어야 한다.

낮음로그인 실패 시 사용자에게 API 의 JSON 에러가 그대로 보인다

콜백이 401·500 으로 끝나면 브라우저가 {"statusCode":500,"message":"Internal server error"} 만 있는 API 주소 화면에 머문다(E2E-004, 005 스크린샷). 프론트로 돌려보내 '로그인에 실패했어요. 다시 시도하세요' 같은 안내를 보이는 편이 낫다. 시나리오 기대에는 없는 동작이라 실패로 치지 않았다.

낮음Google 로그인 화면의 앱 이름이 'supabase_login' 이다

계정 선택 화면에 supabase_login(으)로 이동 이 표시된다(E2E-002 스크린샷). 이전 Supabase 인증용 OAuth 클라이언트를 그대로 쓰는 것으로 보인다. 팀원에게 보이는 이름이므로 OAuth 동의 화면의 앱 이름을 블로그에 맞게 바꾸는 것을 권한다.

참고시나리오 문서와 환경 차이

E2E-011, 012, 014 의 사용자 역할은 '저자(author)'지만 로컬 DB 에는 author 계정이 없다(admin 1명, user 6명). 관리자 계정으로 수행했고, 쓰기 권한 경로는 admin 과 author 가 같다. author 전용 확인은 author 계정을 만든 뒤 다시 해야 한다. E2E-002 의 '302 로 /o/oauth2/v2/auth' 는 curl 에서는 그대로지만 브라우저에서는 Google 이 다시 chooser 로 보내므로 최종 주소가 다르다. 시나리오 문서에 그렇게 적어 두면 헷갈리지 않는다.

참고범위 밖 관찰: 홈 대표 글 커버 이미지가 깨진다

홈 첫 화면의 대표 글 커버(nextjs)가 깨진 이미지로 보인다(E2E-001 스크린샷). 이 글의 cover_image 가 Supabase 스토리지 주소인데 이 환경에서 호스트 이름 해석이 되지 않는다(curl 코드 000). 인증과 무관하며 원인은 확인하지 않았다.

수행 중 한 일과 남은 것

DB. 신규 가입이 500 으로 막혀 데이터를 만들지 못했다. 시작과 끝의 건수가 같다(auth.users 7, posts 53, tags 9). 수동 SQL 은 PREPARE 와 ROLLBACK 만 썼다.

조회수. pnpm test:e2e -- --testPathPatterns=auth 로 auth 스펙만 돌리려 했으나 vitest 가 이 필터를 무시해 4개 스펙(auth, posts, write, swagger) 전체가 실행됐다(13건 통과). posts 스펙은 가장 최근 글 geo 의 조회수를 1 올린다. 이 사실은 tech-blog-neo-api/AGENTS.md 에도 적혀 있는 동작이다. write 스펙은 자체 정리한다. 이후 vitest run --config ./vitest.config.e2e.ts test/auth.e2e-spec.ts 로 auth 스펙만 다시 돌렸다(2건 통과). 시작 전 조회수를 기록하지 않아 값을 되돌리지는 않았다. 글 상세 화면 방문도 조회수를 올릴 수 있다. 현재 geo 는 33.

브라우저. 사용자 브라우저에 localhost 용 session 쿠키(관리자 로그인)가 있었다. 이 쿠키만 따로 백업하고 시나리오마다 지웠다 만들었다가, 끝나고 원래 값과 만료 시각 그대로 복원했다(복원 후 헤더에 관리자 아바타 확인). 다른 쿠키는 건드리지 않았다.

프로세스. 모킹용 :4001, :4002 인스턴스는 종료했다. API(:4000), 프론트(:3000) 개발 서버는 보고서 확인이 끝난 뒤 종료한다.

시나리오별 상세

각 카드는 왼쪽에 시나리오 원문, 오른쪽에 실제 결과를 놓았다. 스크린샷을 누르면 원본 크기로 열린다.

E2E-001

비로그인 상태에서 글쓰기 진입 시 로그인 게이트 노출

P0 · 정상 · 비로그인통과

사전 조건

세션 쿠키 없음. (이 브라우저에는 기존 localhost 세션 쿠키가 있어 session 쿠키만 삭제하고 시작. 종료 시 원본 복원)

테스트 단계

  1. 홈(/)에서 헤더 '글쓰기' 버튼 클릭
  2. /write 화면 확인

기대 결과

'로그인이 필요해요' 안내와 흰색 'Google로 로그인' 버튼이 보이고 에디터는 열리지 않는다. 버튼 링크는 ${NEXT_PUBLIC_API_URL}/auth/google.

실제 결과

홈 헤더에 아바타가 없고 '글쓰기' 버튼은 보였다. 클릭하면 /write 로 이동해 h1 '로그인이 필요해요'와 흰 배경(rgb(255,255,255)) 'Google로 로그인' 버튼이 나왔다.

버튼 href 는 http://localhost:4000/auth/google (NEXT_PUBLIC_API_URL 기본값 기준). 페이지에 textarea·contenteditable 요소는 없었다.

E2E-002

로그인 시작 시 Google 로 리다이렉트되고 state 쿠키 발급

P0 · 정상 · 비로그인통과

사전 조건

GOOGLE_CLIENT_ID / GOOGLE_REDIRECT_URI 설정됨 (.env, 값은 보고서에서 마스킹)

테스트 단계

  1. /write 에서 'Google로 로그인' 클릭 (및 GET /auth/google 직접 호출)
  2. 응답 헤더 확인

기대 결과

302 로 accounts.google.com/o/oauth2/v2/auth 이동. location 에 client_id, redirect_uri, scope=openid email profile, prompt=select_account, state 가 있고 oauth_state 쿠키(HttpOnly, SameSite=Lax, 600초)가 내려온다.

실제 결과

curl: 302 Found, Location 쿼리에 client_id(마스킹), redirect_uri=http://localhost:4000/auth/google/callback, response_type=code, scope=openid+email+profile, state, prompt=select_account. oauth_state 는 Max-Age=600; HttpOnly; SameSite=Lax; Path=/.

브라우저: 버튼 클릭 후 Google 계정 선택 화면에 도착. 브라우저가 가진 oauth_state 쿠키는 HttpOnly, SameSite=Lax, Path=/, 남은 수명 596초, 값 길이 32자(hex 16바이트). 개발 환경이라 Secure 없음.

참고: 브라우저에서는 Google 이 /o/oauth2/v2/auth 를 다시 /v3/signin/accountchooser 로 넘기므로 최종 주소는 문서 표기와 다르다. 302 헤더 자체는 기대와 일치한다.

curl 로 로그인 시작 확인 (client_id·state 마스킹)
$ curl -si http://localhost:4000/auth/google
HTTP/1.1 302 Found
Set-Cookie: oauth_state=<masked>; Max-Age=600; Path=/; Expires=Fri, 06 Nov 2026 09:01:43 GMT; HttpOnly; SameSite=Lax
Location: https://accounts.google.com/o/oauth2/v2/auth?client_id=<masked>&redirect_uri=http%3A%2F%2Flocalhost%3A4000%2Fauth%2Fgoogle%2Fcallback&response_type=code&scope=openid+email+profile&state=<masked>&prompt=select_account
E2E-003

기존 계정(관리자) 이메일로 로그인 완료

P0 · 정상 · 관리자통과

사전 조건

auth.users 에 해당 이메일이 이미 있고 profiles.role=admin. 실제 Google 로그인으로 수행(테스트 더블 미사용).

테스트 단계

  1. /write 에서 Google 로그인 시작
  2. Google 계정 선택 후 동의
  3. 콜백 완료 후 도착 화면 확인
  4. 헤더 확인

기대 결과

FRONT_URL(홈)로 리다이렉트되고 session 쿠키(HttpOnly)가 설정된다. 새 사용자가 생성되지 않고 기존 계정으로 매칭되며 헤더 우측에 아바타가 나타난다. /write 로 자동 복귀하지는 않는다.

실제 결과

계정 선택 화면에서 관리자 계정(yoo32767)만 골랐다. 동의 화면 없이 바로 콜백이 끝났고 http://localhost:3000/(홈)에 도착했다. /write 로 되돌아가지 않았다.

session 쿠키: HttpOnly, SameSite=Lax, Path=/, 남은 수명 6.9999일. document.cookie 에는 보이지 않는다. 로그인 전후 auth.users 행 수는 7로 같았다(신규 생성 없음).

헤더 우측에 아바타 'y'(툴팁 yoo32767)가 나타났다. 이후 /write 는 에디터가 열렸다.

E2E-004

신규 사용자 최초 로그인 시 계정·프로필 자동 생성 (기본 역할 user)

P0 · 정상 · 독자(user)실패

사전 조건

DB 에 없는 이메일의 Google 계정. 실제 계정을 쓸 수 없어 별도 API 인스턴스(:4001)에서 Google 토큰 엔드포인트만 모킹하고 이메일 e2e-new-user@example.test 로 수행.

테스트 단계

  1. Google 로그인 완료
  2. 헤더 아바타(이니셜 또는 Google 사진) 확인
  3. /write 접근
  4. /authors/<username> 접근

기대 결과

auth.users 와 profiles 가 만들어지고 username 은 이메일 앞부분, displayName 은 Google name. 기본 role=user 이므로 /write 에서 '글쓰기 권한이 없어요'. 프로필 페이지는 열리나 글은 0편.

실제 결과

콜백이 500 으로 실패해 로그인 자체가 되지 않았다. 응답은 {"statusCode":500,"message":"Internal server error"}. session 쿠키는 발급되지 않았고 DB 에는 사용자가 생기지 않았다(auth.users 7명 그대로).

서버 로그: error: inconsistent types deduced for parameter $1 (code 42P08, detail: text versus uuid). 원인은 발견 사항 1.

단계 2~4 는 가입이 안 되어 신규 계정으로 확인 불가. 대신 기존 role=user 계정(keyy1315, 테스트 세션 토큰)으로 하위 화면만 확인했다: 이니셜 아바타 'k', /write '글쓰기 권한이 없어요', 프로필 '발행한 글 0편'. 이것은 가입 로직의 증거가 아니라 role=user 화면 동작의 대체 확인이다.

콜백 호출 결과 (curl, 유효 state)
$ [유효 state] GET :4001/auth/google/callback?code=newuser (모킹: 신규 이메일 e2e-new-user@example.test)
